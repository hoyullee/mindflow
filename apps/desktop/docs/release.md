# 새 설치 버전 알리기·새 판 내보내기

[`../README.md`](../README.md)(색인·자주 쓰는 명령)에서 옮긴 원문입니다.

## 새 설치 버전 알리기

앱 *화면*은 껍데기가 원격 출처를 띄우므로 **웹 배포가 곧 최신 판**이다. 그런데
**껍데기 자신**(`.exe`/`.dmg`)은 스스로 갱신되지 않아서, 새 설치 파일이 올라와도
앱 안에서 알 길이 없었다. 그래서 **설정 › 버전 확인**의 `업데이트` 구획이
**화면과 껍데기를 합쳐 한 행으로** 말한다.

| 무엇이 새로운가 | 행이 하는 말 | `업데이트`를 누르면 |
| --- | --- | --- |
| 화면만 | `새 버전이 준비됐어요` | 그 자리에서 적용(리로드) |
| 껍데기만 | `새 설치 버전 0.3.0이 있어요` | 받는 페이지가 열린다 |
| 둘 다 | 같은 말 + `설치하면 화면까지 함께 최신이 돼요` | 받는 페이지가 열린다 |

**행을 둘로 두지 않는 이유**는 정할 것이 없기 때문이다 — **껍데기를 새로 설치하면
앱이 다시 실행되면서 대기 중인 서비스 워커가 활성화되므로 화면까지 함께 최신이
된다**(그 출처의 페이지가 전부 닫히는 것이 활성화 조건이다). 그래서 둘이 함께
있으면 껍데기 쪽이 이긴다. 다만 **진행 중인 웹 작업**(적용 중·저장 실패로 멈춤)은
껍데기보다 먼저다 — 리로드가 임박한 자리를 다운로드 버튼으로 갈아 끼우면 사용자가
그 사이에 앱을 떠난다. 이 우선순위는 순수 함수 `mergedUpdateState`가 정하고
테스트가 지킨다.

```
apps/web/src/platform/shellUpdate.ts   순수 판정(버전 비교·매니페스트 파싱)
apps/web/vite.config.ts                desktopVersionManifest 플러그인
```

- **버전의 정본은 `apps/desktop/package.json` 하나**다. 웹 빌드가 그 파일을 읽어
  `dist/desktop-version.json`을 만든다 — 값을 두 곳에 적지 않으므로 갈릴 수 없고,
  갈린 값은 "새 버전이 있다"는 **거짓말**이 된다.
- **읽지 못한 것과 최신인 것을 가른다.** 파일이 없거나(배포 전) 모양이 이상하면
  `unknown`이고 화면은 "확인하지 못했어요"라 말한다 — 최신이라고 말하지 않는다.
- **PWA 프리캐시 글롭에 `json`이 없어야 한다.** 넣으면 이 파일이 캐시에 굳어
  영영 옛 버전을 읽는다(`shellUpdate.test.ts`가 그 계약을 지킨다 — 틀려도 빌드와
  테스트가 통과하고 앱을 설치해 봐야 드러나는 종류다).
- 버튼 이름은 세 경우 모두 `업데이트`다(사용자의 뜻이 그것이다). 대신 **부제가
  무슨 일이 일어나는지 말한다** — 껍데기 쪽은 `받는 페이지가 열려요`라 적는다
  (릴리스 페이지를 시스템 브라우저로 열고 설치는 사용자가 한다).

### 말을 거는 자리는 홈 LNB 알림 하나다

예전에는 화면 하단 토스트가 "새로고침할까요?"를 물었다. 그 자리는 **편집 중에
끼어드는 자리**였고, 알림 창구(LNB)가 생긴 뒤로는 같은 소식이 두 곳에서 말해졌다.
지금은 이렇게 갈린다:

| 어디서 | 무엇을 하나 |
| --- | --- |
| 랜딩·약관·빈 로그인 폼 | 예전 그대로 **즉시 조용히 적용**(잃을 것도, 알릴 창구도 없다) |
| 홈·유휴 에디터 | 보고 있으면 **LNB 알림**으로 알리고 기다린다 · 탭을 떠나면 조용히 적용 |
| 입력·편집 중 | 아무것도 하지 않는다(`block`) |

그래서 홈의 유휴 위험도가 `safe`가 아니라 **`defer`**다(`features/home/updateRisk.ts`)
— `safe`면 보고 있는 화면이 눈앞에서 갈아끼워져 그 알림이 뜰 자리가 없다. 대부분의
사용자는 탭을 떠나는 사이에 조용히 최신이 되고, 보고 있는 사람만 LNB에서 누른다.

알림은 목록 **맨 위 고정 한 줄**이고(사건이 아니라 상태라 시간순 묶음 밖에 있다)
누르면 설정 › 「버전 확인」이 열린다. 열어도 사라지지 않는다 — 적용하거나 설치할
때까지 끝나지 않는 일이다. **껍데기 새 판은 자동 적용이 아예 없으므로 이 알림이
사용자가 그것을 알 수 있는 유일한 길**이다.

```
apps/web/src/pwa/UpdatePrompt.tsx         적용만 한다(웹·껍데기 상태를 모듈에 올린다)
apps/web/src/pwa/updateControl.ts         그 상태와 손잡이 · `useMergedUpdate`
apps/web/src/platform/shellUpdate.ts      `updateNoticeOf` — 알릴 만한 상태인가
apps/web/src/features/home/components/NotificationBell.tsx  고정 한 줄
```

`updateNoticeOf`는 **사용자가 손을 쓸 수 있는 상태만** 돌려준다(껍데기 새 판·웹 새
판·저장 실패). 확인 중·최신은 `null`이다 — 알림 창구에 늘 무언가 있게 만들면 그
창구가 신호를 잃는다.

### 새 판을 내보내는 절차

```bash
# 1) 셸 버전을 올린다 — 이 값이 매니페스트·설치 파일 이름·app.getVersion() 전부다
#    (apps/desktop/package.json의 "version")
# 2) 커밋하고 라이브까지 배포한다(매니페스트는 웹 배포에 실린다)
# 3) 태그를 밀면 워크플로가 설치 파일을 만들고 릴리스에 붙인다
git tag desktop-v0.3.0 && git push origin desktop-v0.3.0
```

**태그 이름은 버전을 정하지 않는다** — 정본은 1)의 `package.json`이고 태그는
릴리스에 붙는 **이름표**다. 그래서 둘이 어긋날 수 있는데, 어긋나면 릴리스 제목은
`desktop-v0.3.0`인데 그 안의 파일은 `Geurio Setup 0.2.0.exe`이고 매니페스트도
0.2.0이라 **아무에게도 "새 설치 버전이 있어요"가 뜨지 않는다**(빌드도 테스트도
초록이라 받아서 눌러 봐야 안다). `plan` 잡의 `Check tag matches shell version`이
태그로 돌 때 그 둘을 대조해 **빌드 전에** 멈춘다 — `build`가 아니라 거기서 막는
이유는 러너를 하나도 태우지 않기 때문이다(태그 푸시는 둘을 만들고 macOS는 분당
과금이 ubuntu의 10배다). 1)을 잊고 태그하면 30초 만에 이유를 말하고 끝난다.

태그 푸시는 **Windows·macOS 둘만** 만들고 `Attach to release` 스텝이 `gh`로
릴리스를 만들어 산출물을 올린다. **Store 패키지(`.appx`)는 만들지 않는다** —
지금 MSIX는 개발용 자가서명이라 받는 사람이 설치할 수 없는데, 릴리스에 `.exe`·
`.dmg`와 나란히 놓이면 어느 것을 받아야 하는지 흐려진다(Partner Center 정체성으로
바꿔 설치 가능해지면 `plan` 잡의 그 분기를 지운다). Store 패키지가 필요하면
`Run workflow`에서 `store`를 직접 고른다 — 그때는 릴리스에 붙지 않는다. matrix 잡이 동시에 돌기 때문에
먼저 도착한 잡이 릴리스를 만들고 나머지는 그 릴리스에 올린다(`create`는 이미
있으면 삼키고 `upload --clobber`가 덮어쓴다).

**아티팩트로는 안 된다** — 14일 만료 + GitHub 로그인이 필요해서 앱이 안내할
주소가 될 수 없다. 릴리스는 만료가 없고 공개 저장소에서는 로그인 없이 받힌다
(저장소를 비공개로 바꾸면 로그인이 필요해지므로, 그때는 매니페스트의 `url`을
다른 곳으로 돌린다 — 그 값은 **데이터**라 앱 코드를 고치지 않는다).
