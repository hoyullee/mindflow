## 19. 구글 캘린더 연동 (PR5 겹치기 + PR6 쓰기) — 서버 없는 연동

일정 화면에 사용자의 **구글 일정을 겹치고**(PR5), 그 자리에서 **만들고 고치고 지운다**
(PR6). 마이그레이션도 Edge Function도 없다 — 브라우저가 구글 API를 직접 부르고, 우리는
**아무것도 저장하지 않는다.**

### 왜 저장하지 않나

받아 온 일정을 우리 DB에 넣으면 두 곳의 진실이 갈린다(구글에서 지운 일정이 우리 쪽에
남는다). 동기화라는 큰 문제를 새로 떠안는 대신 **보이는 달치를 그때그때 받아 화면에만**
겹친다 — 구글이 언제나 옳다. 저장하는 것은 사용자의 **선택**뿐이고(`workspaces.data.google
= { calendars: [...] }`) 그건 기존 per-user 블롭에 실려 기기 간에 따라온다.

액세스 토큰은 **블롭에 오지 않는다.** 한 시간짜리이고 기기·탭마다 다르므로 **이 기기**
(localStorage `mf_gcal_token`)에 두고, 옛 탭 저장소 값은 읽을 때 한 번 이사시킨다.

**만료되면 조용히 다시 받지 않는다** — GIS 토큰 요청은 `prompt: ''`(조용한 갱신)여도
**팝업 창을 연다**(이 API에는 iframe 갱신이 없다). 그래서 토큰이 없거나 만료됐으면
`needsReauth`를 세우고 화면이 `다시 연결`로 말한다(사용자 제스처에서만 GIS를 부른다).

> **"배포하면 연동이 풀린다"는 제보의 정체**: 풀리지 않는다 — 고른 캘린더는 블롭에
> 그대로 있고 끊긴 것은 한 시간짜리 **토큰**이다. 배포가 강제 리로드를 일으켜 그 만료가
> 드러나는 것이라, `다시 연결` 툴팁·설정 부제가 "다시 연결하면 고른 캘린더가 그대로
> 이어진다"고 밝힌다. **지금은 서버가 대신 갱신한다** — 아래 「연결 유지 — refresh
> token」 참고. 그 흐름이 없는 배포(로컬·데모·함수 미배포)에서만 위 문단대로 굴러간다.

### 인증이 로그인과 따로인 이유

로그인은 GIS **ID 토큰** 흐름이라(§1d) API 스코프를 주지 않는다. 캘린더를 다루려면
**액세스 토큰**이 필요하고, 그건 GIS의 다른 API(`google.accounts.oauth2.initTokenClient`)다.
로그인에 스코프를 묶지 않은 것은 구글이 권하는 **점진적 승인**이기도 하다 — 캘린더를 안
쓰는 사람에게 캘린더 권한을 묻지 않는다.

요구하는 스코프는 **딱 두 개**다(`GOOGLE_CALENDAR_SCOPES`):

| 스코프 | 왜 필요한가 |
| --- | --- |
| `.../auth/calendar.events` | 일정 읽기·**쓰기**(만들기·고치기·지우기) |
| `.../auth/calendar.calendarlist.readonly` | "어느 캘린더를 겹칠까"를 고르게 하는 **목록** — `calendar.events`는 목록을 주지 않는다 |

전체 권한(`.../auth/calendar`)은 받지 않는다 — 캘린더 자체를 만들거나 지우지 않으므로
요구할 근거가 없고, 검수도 스코프마다 "왜 필요한가"를 묻는다.

**승인된 스코프를 토큰과 함께 적어 둔다.** 사용자가 동의 화면에서 일부만 체크할 수 있고,
스코프를 넓힌 배포 뒤 옛 토큰이 남을 수도 있다 — 그러면 읽기는 되는데 **쓰기만 403으로
조용히 죽는다.** `scopeCovers`가 모자란 토큰을 **없는 것으로 보고**, 화면은 `다시 연결`을
권한다(설정 구획의 버튼 + 일정 화면·위젯 머리의 아이콘).

### 배포 전 필요한 것 — **콘솔 작업 + 앱 검수**

두 스코프 모두 구글이 **민감(sensitive)** 으로 분류한다. 아래를 마쳐야 일반 사용자에게
열린다. **읽기·쓰기를 한 번에 넣는다** — 심사는 스코프 묶음 전체를 한 사이클로 보므로,
읽기만 먼저 통과시키면 쓰기를 얹을 때 절차를 처음부터 다시 밟는다.

1. [Google Cloud Console](https://console.cloud.google.com/) → **API 및 서비스** →
   **라이브러리**에서 `Google Calendar API`를 **사용 설정**한다.
2. **OAuth 동의 화면**(개편 후 `Google 인증 플랫폼` → `데이터 액세스`) → 범위 → 위
   표의 스코프를 **다섯 개 모두 추가**한다(§1d에서 만든 그 동의 화면이다 —
   클라이언트 ID도 그대로 쓴다. `VITE_GOOGLE_CLIENT_ID`는 이미 있다).
   `calendarlist.readonly`는 **비민감**으로 분류되므로 정당성·영상은 나머지 넷만 필요하다.
   People API(이름 검색)와 Admin SDK Directory(회의실)도 **1번처럼 사용 설정**해야 한다.
3. 동의 화면의 **승인된 자바스크립트 원본**에 `https://geurio.com`(+ 프리뷰 도메인)이
   들어 있는지 확인한다 — 토큰 요청도 이 목록을 본다.
4. **앱 검수 제출.** 검수에는 보통 앱 사용 영상과 스코프가 필요한 이유 설명이 요구된다
   (쓰기 스코프는 심사가 더 깐깐하다 — 영상에 만들기·고치기 흐름을 담는다).

   검수 전 동작은 **게시 상태**에 따라 갈린다(`대상`/Audience 탭):

   | 게시 상태 | 검수 전 동작 |
   | --- | --- |
   | `테스트` | **테스트 사용자 목록**(최대 100명)의 계정만 쓸 수 있다. 목록에 없으면 `앱이 차단됨` |
   | `프로덕션` | 테스트 사용자 목록은 **무시된다.** 누구나 `확인되지 않은 앱` 경고 → `고급` → 계속 이동으로 통과할 수 있고, 동의한 사용자 100명 한도가 있다 |

   ⚠️ 이미 `프로덕션`이면 **`테스트`로 되돌리지 말 것** — 목록에 없는 **모든 실사용자의
   구글 로그인이 즉시 막힌다**(경고 화면은 클릭으로 통과되지만 테스트 모드 차단은 통과할
   방법이 없다).

**그 전까지 앱은 아무것도 달라지지 않는다.** 설정의 `연동` 구획은 `VITE_GOOGLE_CLIENT_ID`가
없으면 **그리지도 않고**, 있어도 사용자가 직접 `연결`을 누르기 전에는 아무 요청도 나가지
않는다. 스코프가 없는 상태에서 눌러도 구글이 거절하고 그 문구가 구획에 뜬다.

### 검수 기록 (2026-09-01 1차 회신)

통과: 브랜드 가이드라인 · 최소 범위 요청. 지적 둘:

1. **개인정보처리방침** — "Google 사용자 데이터를 **누구에게** 공유·전송·공개하는지
   명시되어 있지 않다." §4의 "제3자 제공하지 않음" 한 줄로는 부족했다 — 검수는
   공유·전송·공개 세 낱말을 제목으로 단 **눈에 띄는 구획**과 예외(위탁·법령·동의·
   사업 이전)의 명시적 열거, 그리고 **로그인 프로필 정보까지 포함한** Google 사용자
   데이터 전체를 본다. → `/privacy`에 §5 「Google 사용자 데이터의 공유·전송·공개」
   신설로 대응(라이브 반영 후 신뢰안전팀 메일 스레드에 **답장해야** 재검토가 돈다 —
   콘솔 화면의 안내문이 그렇게 말한다).
2. **앱 기능** — 콘솔 패널에는 세부 사유가 없다. **신뢰안전팀 메일에 적힌 세부 내용**을
   확인해 대응할 것(흔한 사유: 데모 영상이 스코프 사용 흐름을 안 담음 · 심사자가 앱에
   들어가 기능을 확인할 수 없음 — 테스트 계정·영상 문제).

홈페이지 요구사항은 "검토 중"(지적 아님). 지적 대응 중에도 **스코프·게시 상태·브랜딩은
바꾸지 말 것** — 통과한 항목이 재검토로 되돌아간다.

**메일 세부(같은 날 도착, Third Party Data Safety Team)** — 앱 기능 지적의 실체는
**"요청한 모든 스코프의 실제 동작을 시연하라"**다. 시연 대상으로 콕 집은 넷(비민감인
`calendarlist.readonly`는 빠져 있다 — §위 표와 일치):

| 스코프 | 데모 영상에 담아야 하는 장면 |
| --- | --- |
| `calendar.events` | 연동 동의 화면(앱 이름·스코프 목록이 보이게) → 일정 화면에 구글 일정 표시 → **Geurio에서 구글 목적지로 일정 생성·수정·삭제** → 구글 캘린더 웹에서 반영 확인 |
| `directory.readonly` | 새 일정 참석자 입력에 **조직 구성원 이름** 타이핑 → 이름·이메일 후보 → 골라서 초대 |
| `contacts.other.readonly` | 같은 입력에서 **조직 밖, 메일을 주고받은 적 있는 사람**이 후보로 뜨는 장면 |
| `admin.directory.resource.calendar.readonly` | 새 일정의 **회의실 목록** → 골라 예약됨 → 만든 일정에 회의실이 붙은 것(구글 캘린더에서) 확인 |

주의: 뒤의 셋은 **Workspace 조직 계정**(회의실이 등록된)이어야 화면에 값이 나온다 —
개인 @gmail 계정으로는 시연 자체가 불가능하다. 시연할 수 없는 스코프는 콘솔에서
**빼고 재제출하는 것이 정당한 대응**이다(앱은 그 스코프 없이도 동작하게 이미 설계돼
있다 — 참석자는 이메일 직접 입력, 회의실 구획은 안 뜸). 절차(메일 원문): ① 방침·영상을
고치고 **Cloud Console에서 재제출** ② **그 메일에 직접 답장**해야 재검토가 돈다.

### 검수 기록 (2026-09-03 2차 회신)

1차 지적(§5 공유·전송·공개 · 데모 영상)을 고쳐 재제출한 뒤 온 회신. **지적 하나**:

> Your privacy policy does not specify any data protection mechanisms for sensitive data.

**§5와 다른 항목이다.** 검수는 항목별 체크리스트라 한 번에 하나씩 온다 — §5는
"누구에게 주는가"(공유·전송·공개), 이번 것은 **"어떻게 지키는가"**(전송·저장 암호화,
접근 통제, 비밀 키 관리, 안전한 삭제)다. 우리 방침에는 그 구획이 **아예 없었다**
(1~9항: 수집·목적·위탁·캘린더·공유·보유·권리·문의·변경).

→ `/privacy`에 **§6 「데이터 보호 조치」** 신설(이후 번호 한 칸씩 밀림, 7~10). 담은 것:
HTTPS(TLS) · 저장 시 암호화 · **RLS 계정 단위 접근 통제** · 첨부 파일 비공개 버킷 +
서명 URL · 비밀 키는 서버 시크릿만 · 세션 보호(전체 로그아웃·비번 변경 시 타 세션 해지) ·
최소 수집(캘린더 데이터 미보관) · 안전한 삭제(탈퇴 cascade) · 사고 대응.

**곁들여 잡은 것 — 방침이 사실과 어긋나 있었다**: §4의 접근 토큰 문장이
`sessionStorage`·"탭을 닫으면 사라집니다"였는데, 연동이 자꾸 해제된다는 제보로 토큰을
`localStorage`로 옮기면서(#PR A) **코드만 바뀌고 방침이 남았다**. 보호 수단을 적는
구획이 생기는 김에 실제 구현과 맞췄다(회귀 테스트가 `sessionStorage` 문구 부재를 고정).
**교훈: 저장 위치·수명·암호화·권한 정책을 바꾸면 §4·§6을 함께 고칠 것** — 방침이
사실과 다르면 그 자체가 반려 사유다.

절차는 1차와 같다: ① 라이브(`geurio.com/privacy`)에 반영 ② Cloud Console에서 재제출
③ **그 메일에 직접 답장**해야 재검토가 돈다. 스코프·게시 상태·브랜딩은 건드리지 않는다.

### 어떻게 도는가

| 시점 | 하는 일 |
| --- | --- |
| 설정 → `연결` | `initTokenClient({prompt:'consent'})` → 동의 → 액세스 토큰 |
| 연결 직후 | `calendarList` 조회 → **기본 캘린더 + 공휴일**만 켜서 저장 |
| `캘린더 추가` | 그 주소로 `events?maxResults=1` 한 번 → 읽히면 이름(응답의 `summary`)과 함께 블롭 `google.extra`에 적고 켠다. **구독 API는 부르지 않는다**(아래) |
| 일정 화면·위젯 | 고른 캘린더마다 `events?singleEvents=true`로 **보이는 6주** 조회 |
| 토큰 만료(401) | `prompt:''`로 **한 번** 조용히 재발급 후 재시도 |
| 새 일정 → 목적지 `Google` | `POST /calendars/{id}/events` → 보이는 달 재조회 |
| 상세에서 고치기 | `PATCH .../events/{eventId}` + `If-Match: etag` → 재조회 |
| 칩을 끌어 날짜 옮기기 | 같은 `PATCH`(기간은 길이를 지킨 채 평행이동) |
| 상세에서 삭제 | `DELETE .../events/{eventId}` |
| `연결 해제` | 토큰 폐기(`revoke`) + 블롭의 `google` 삭제 |
| **탭 복귀·창 포커스·네트워크 복귀** | 보이는 달을 다시 받는다(20초 스로틀) |
| **보고 있는 동안 60초마다** | 같은 재조회 — 가려진 탭은 쉰다 |
| 회의실 행(새 일정·상세) | `GET /calendars/{회의실}/events?timeMin..timeMax` → `사용 중`/`사용 가능` |

**만들 때 우리가 보내는 것 — 참석자 규칙**(요청): 새 일정의 `attendees`에는 화면에서 초대한
사람과 회의실 말고 **나 자신**도 들어간다(`{ email: 내 주소, responseStatus: 'accepted' }`).
구글은 캘린더 화면에서 만든 일정에는 주최자 행을 자동으로 넣어 주지만 **API로 만든 일정에는
넣어 주지 않아서**, 내 응답이 없어 상세 팝업의 「참석 여부」 구획이 통째로 사라졌다.
**사람을 한 명이라도 초대한 일정에만** 넣는다 — 혼자 적어 둔 일정을 "참석자 1명짜리 회의"로
만들지 않는다. 회의실만 잡은 일정도 넣지 않는다. `organizer`는 **보내지 않는다**: 구글이
그 일정이 사는 **캘린더의 주인**으로 정하는 값이다(그래서 팀 캘린더에 만들면 주최자가 그
캘린더이고 `creator`가 나다 — 화면은 `creator`를 먼저 읽어 "일정을 만든 사람"을 말한다).

**회의실이 예약을 거절하면**(요청): 구글의 회의실 캘린더는 이중 예약되면 스스로 초대를
거절한다(`responseStatus: 'declined'`). 새 왕복도 새 스코프도 없이 이미 받아 둔 응답에서
읽어(`declinedRooms`) 만든 직후 토스트 · 상세 팝업의 경고 줄 · 달력 칩의 `⚠`로 말한다.
**알림 센터·웹 푸시로는 내보내지 않는다** — 서버가 캘린더를 모르므로 새 표와 cron Edge
Function이 필요하고, 민감 스코프를 서버에서 쓰는 순간 재검수 위험이 붙는다.

`singleEvents=true`로 받는 이유는 **반복 규칙(RRULE)을 우리가 해석하지 않기 위해서**다 —
구글이 회차로 펼쳐 주므로 화면에 놓을 날이 그대로 나온다.

### 회의실이 그 시간에 비어 있는가 (요청)

구글 캘린더는 회의실 충돌을 **달력에 겹쳐** 보여 주지만 우리는 팝업이라 그럴 자리가
없다. 그래서 **회의실 행 자체가** 말한다 — `사용 중` / `사용 가능`, 그리고 **모르면
아무 말도 하지 않는다**(조직이 그 회의실 캘린더를 공개하지 않으면 403이다. "사용
가능"이라 잘못 말하는 것보다 침묵이 낫다).

**사용 중인 방을 고를 때는 한 번 묻는다**(요청) — 겹쳐 잡는 것이 의도인지 확인하고,
확인을 거쳐 잡으면 배지가 `겹쳐 예약`으로 **두 사실을 함께** 말한다(`사용 중`만 남기면
내가 잡았다는 사실이, `예약됨`만 남기면 겹친 사실이 사라진다). 이미 고른 방을 빼는
클릭은 묻지 않는다.

**누가 쓰고 있는가**(요청)도 같은 조회에서 나온다 — `checkRoom`이 불리언이 아니라
`{ busy, by, title, from, to }`를 돌려주고, 행의 툴팁과 (골랐을 때) 이름 아래 한 줄이
`사용 중 · 이호율 · 디자인 리뷰 · 09:00–09:30`처럼 보여 준다(`roomBusyLabel`). 회의실
캘린더를 "한가함/바쁨만"으로 공개해 두면 제목·주최자가 없이 시각만 오고, 그때는 화면도
시각만 말한다 — **없는 것을 지어내지 않는다.**

**새 스코프는 받지 않았다.** 구글의 `freeBusy.query`는 스코프가 따로여서
(`calendar.freebusy` 계열) 그걸 쓰려면 동의 화면을 고치고 **검수를 다시 받아야** 한다.
회의실도 결국 캘린더이므로, 이미 승인된 `calendar.events`로 그 캘린더의 **그 구간만**
물어보면 같은 답이 나온다(`calendar/googleDirectory.ts`의 `checkRoom`). 취소된 일정,
회의실이 스스로 거절한 초대, 그리고 **지금 고치고 있는 그 일정**은 제외한다(자기 자신과
부딪힌다고 말하지 않게).

왕복은 목록 전부(앞의 60개까지)를 **네 개씩 이어 달려** 묻고, 250ms 디바운스와
`이메일|구간` 캐시가 붙는다 — 수십 개를 한꺼번에 날리면 구글이 속도 제한으로 되돌려
보내 배지가 통째로 빈다.
구간은 팝업의 **초안**을 따라간다 — 저장된 시각만 보면 시간을 고치는 동안 어긋난 답을
보여 준다.

### 위치의 지도 (요청)

구글 캘린더처럼 **입력 중 장소를 자동완성**하려면 Places API가 필요하다: 별도 API 키와
결제 계정이 있어야 하고(그 키는 브라우저로 실려 나가므로 도메인 제한·사용량 관리가 함께
따라온다) 무료 한도가 없다. 그래서 지금은 자동완성 대신 **적어 둔 주소를 지도에서 여는
길**만 둔다(`지도에서 보기` — 키도 비용도 필요 없다). 자동완성이 필요해지면 그때 Places를
켜는 결정을 따로 하면 된다.

### 열어 둔 채 밖에서 바뀐 것 (제보)

구글이 정본이므로 **다시 물어야** 한다 — 일정 화면을 열어 둔 채 구글 캘린더에서 일정을
더하면 우리 달력은 그대로였다(제보). 서버가 없으니 푸시(watch 채널)를 받을 수 없어,
서버 없이 되는 두 계기로 재조회한다(`calendar/useLiveRefresh.ts` — Geurio 일정도 같은
훅을 쓴다: 다른 기기에서 바뀐 경우가 같은 처지다):

1. **깨어나는 순간** — 탭 복귀·창 포커스·네트워크 복귀. 확인하러 돌아오는 바로 그
   순간이 자연스러운 타이밍이고 브라우저는 이때 스스로 묻지 않는다(20초 스로틀로
   포커스+visibility 연타를 거른다).
2. **주기** — 보고 있는 동안에만 60초. 가려진 탭은 쉬었다가 복귀 때 ①이 받는다.

캘린더 **목록**은 이 주기에 넣지 않는다(캘린더가 새로 생기는 일은 드물고, 조회가
배로 는다 — 설정을 열면 그때 다시 받는다). 캐시가 있어 받는 동안 화면이 비지 않고,
새 값이 오면 조용히 갈아 끼운다.

### PATCH는 **바뀐 것만** 보낸다 (제보)

제목 한 글자를 고쳤는데 `start`가 함께 실려 있으면, 구글이 그 시각을 거절하는 순간
(`400 Invalid start time.`) **제목 수정까지 통째로 막힌다**. 그 사이 날짜가 옮겨져
있으면 같은 이유로 `412`도 난다 — 둘 다 사용자가 손대지 않은 필드 때문이다.

- 상세 팝업의 저장은 `patchFrom`이 **바뀐 키만** 담는다(제목만 고치면 `summary` 하나).
- 끌어서 날짜를 옮기면 `start`+`end` **짝만** 간다(구글은 `date`/`dateTime`이 섞이면
  거절하므로 언제나 짝이다).
- 빈 값은 여전히 **빈 문자열·빈 배열로** 보낸다(키를 빼면 "안 바꾼다"로 읽혀 지운 것이
  저장되지 않는다).
- `412`의 비교 범위도 **그 PATCH가 쓰는 필드**뿐이다(`managedFieldsDiffer(a, b, only)`).
  보내지 않는 필드가 달라진 것은 충돌이 아니다 — PATCH는 보낸 키만 바꾸므로 남의
  변경을 덮지도 않는다.
- **`patch`는 중첩 객체까지 필드 단위로 병합한다** — 이것이 라이브의
  `400 Invalid start time.`을 만든 지점이다: 저장된 `start: { date }` 위에
  `start: { dateTime }`을 보내면 병합 결과가 `{ date, dateTime }` **둘 다 있는
  상태**가 되어 거절된다(종일 ↔ 시각을 오갈 때마다, 양방향으로). 그래서 PATCH는
  쓰지 않는 쪽을 **`null`로 지운다**(`whenBody(d, true)` — 구글의 patch에서 `null`은
  "이 필드를 비워라"다). insert(POST)에는 지울 것이 없으므로 넣지 않는다.
- `400`은 **우리 요청이 틀렸다**는 뜻이라 "잠시 후 다시"가 거짓말이 된다: 구글이 준
  `error.message`를 화면 문장에 담고(`구글이 이 요청을 거절했어요: …`) 콘솔에는 보낸
  본문까지 남긴다(`[geurio] 구글이 요청을 거절했어요:`). 다음 제보를 진단할 단서다.

### 쓰기 규칙 셋

#### 구독하지 않은 캘린더를 목록에 더하기(요청)

`보여 줄 캘린더`는 **구독한 캘린더**(`calendarList`)만 담는다 — 구독은 구글 쪽
개인 북마크이고 그 목록에 넣는 API(`calendarList.insert`)는 **쓰기 스코프가 따로**라
동의 화면을 고치고 **검수를 다시 받아야** 한다. 통과한 다섯 스코프를 건드리지 않기로
했으므로(위 표) 목록은 **그리오 쪽에만** 더한다:

- 저장 위치는 워크스페이스 블롭의 `google.extra = [{ id, name }]`(스페이스·테마와 같은
  per-user 블롭이라 기기 간에 따라온다). `calendars`는 그대로 "지금 보여 주는 id"다.
- 확인·이름은 `events.list` **한 번**으로 얻는다(`probeCalendar`) — 그 API는 접근할 수
  있는 **어느 캘린더 id로도** 되고 응답 머리에 그 캘린더의 `summary`가 실려 온다.
- 못 읽으면 사유를 갈라 말한다(404 주소 오류 / 403 권한 없음 / 400 형식 오류).
- **구글 구독 목록과 다른 점 둘**: 색은 `calendarList`에만 있으므로 우리가 id를 씨앗으로
  정하고, `accessRole`을 알 수 없으므로 **보기 전용**으로 둔다(새 일정 목적지에 오르지
  않고 그 일정도 고칠 수 없다 — 모르는 것을 할 수 있다고 말하지 않는다).
- 나중에 사용자가 구글에서 그 캘린더를 실제로 구독하면 `calendarList` 쪽이 이기고
  우리 항목은 조용히 승격된다(색·쓰기 권한이 그때 붙는다).
- **공휴일 캘린더는 id로 표식한다**(`isHolidayCalendarId`) — 이 표식이 곧 "칩이 아니라
  날짜를 칠한다"는 규칙의 스위치이므로, 더한 항목에 세우지 않으면 그 캘린더의 항목이
  달력에 **칩으로 늘어선다**(구독한 공휴일 캘린더는 `parseCalendarList`가 같은 규칙으로
  세운다).

#### 공휴일 국가(요청)

공휴일은 구글의 **공개 캘린더**에서 온다(`ko.south_korea#holiday@…`). 그래서 국가를
고르는 일은 그 캘린더를 목록에서 **갈아 끼우는 일**이고 새 스코프도 조회도 필요하지 않다:

- 표는 `HOLIDAY_COUNTRIES`(한국·일본·미국) 하나이고, 저장은 블롭 `google.holiday`다.
  값에는 **`off`(없음)**도 있다(`HOLIDAY_OFF`) — 공휴일을 끄는 유일한 스위치다.
- 고르면 **표의 세 나라 공휴일 id를 전부** `calendars`·`extra`에서 빼고 그 나라를 넣는다
  (`isManagedHolidayId`). 구독하지 않은 국가는 `extra`로 들어간다(위 규칙 그대로 —
  `events.list`로 읽힌다). 두 나라가 함께 켜져 같은 날을 두 번 칠하는 상태를 만들 수 없다.
- **표의 세 나라 공휴일 캘린더는 `보여 줄 캘린더` 목록에 넣지 않는다**(제보: 설정에서
  국가를 고르게 해 두고 목록에서도 체크하게 되어 있어 공휴일이 두 번 표시되는 것처럼
  보였다). 스위치는 캘린더마다 하나다 — 표에 없는 공휴일 캘린더(예: 사용자가 주소로 더한
  `en.south_korea#holiday`)는 세그먼트가 관리하지 않으므로 평범한 행으로 남는다.
- 저장된 값이 없으면 **목록에 든 공휴일 캘린더**가 지금 국가를 말하고, 그것도 없으면
  `off`다 — 예전 폴백은 `kr`이라 공휴일을 안 보고 있는 사람에게 "한국"이 켜진 채로
  보이는 거짓말이었다.
- UI는 **연결된 뒤에만** 그린다(연결 전에는 고를 수 있는 척만 하게 된다).

#### 설정에서 어디에 있나(요청)

연동은 **설정 › 계정 설정 › Google 캘린더 연동**(한 겹 더)이다 — 계정 설정에는 진입
행만 있고, 보여 줄 캘린더·캘린더 추가·공휴일 국가가 그 화면 안에 있다. 조회도 그
화면이 열려 있을 때만 돈다(`mode`가 `'events'`). 그래서 진입 행의 부제는 **왕복 없이
되는 값**(블롭의 `enabled`·`calendars`)으로만 만든다: `connected`는 목록이 도착해야
참이 되므로 그것으로 문구를 고르면 연동해 둔 사람에게 "연결하면 …"이라 말하게 된다.

`connected`는 그래서 **파생값**이다 — `enabled && !needsReauth`, 즉 "블롭이 켜져 있고
끊겼다고 알려진 바 없다". **"이 탭이 지금 액세스 토큰을 들고 있는가"가 아니다**: 그
토큰은 한 시간마다 만료되고 refresh token은 서버에만 있으므로, 토큰의 유무로 화면을
고르면 하루 뒤에 돌아온 사용자에게는 연결해 둔 것이 없는 것처럼 보인다(제보: 연동
화면이 짧게 떴다가 목록이 오며 커졌다 — 실측 구획 95px, 팝업 카드 570 → 220px).

목록의 로딩 판정도 같은 결이다 — **"목록이 비어 있는가"로 보지 않는다**: 화면이 쓰는
목록은 구독 목록 ∪ **주소로 더한 캘린더**(블롭에 있어 조회 없이 즉시 나온다)라, 더해 둔
것이 하나라도 있으면 "이미 왔다"로 오판해 스켈레톤을 건너뛴다(제보: 그 한 줄 높이로
팝업이 줄었다가 목록이 오며 커졌다). 훅이 `listLoaded`로 **구독 목록이 도착했는지를
직접** 들고, 화면은 그 값만 본다.

그래서 "끊겼다"고 말할 수 있는 것은 둘뿐이다: **갱신이 실패했다**(`needsReauth` — 구글
에서 권한을 회수했거나 서버 흐름이 없는 환경) 또는 **사용자가 껐다**(`enabled` 거짓).
"지금 조회하지 않는다"(문서 위젯·닫힌 설정의 `mode: 'off'`)와 홈 하이드레이션 전은
**아직 모른다**이지 끊긴 것이 아니다.

- **쓸 수 있는 캘린더만.** `calendarList`의 `accessRole`이 `owner`/`writer`면
  `writable`이다. 공휴일 캘린더와 남이 보기 전용으로 공유한 캘린더는 새 일정 **목적지에
  오르지 않고**, 그 일정의 상세도 읽기 전용으로 뜬다(진짜 게이트는 구글의 권한이고, 이건
  "고쳐지는 척하는" 화면을 막는 어포던스다).
- **반복 일정은 이 회차만.** `singleEvents=true`로 펼쳐 받은 회차 id에 그대로 쓰므로 그
  회차만 바뀐다. 반복 규칙 자체는 구글에 맡긴다(상세 팝업이 그렇게 말한다).
- **덮어쓰기 방지.** 수정은 받아 둔 `etag`를 `If-Match`로 싣는다 — 그 사이 구글에서
  바뀌었으면 412로 막히고 "다시 시도해 주세요"가 뜬다.

빈 위치·메모는 **빈 문자열로** 보낸다. `PATCH`에서 키를 빼면 구글은 "안 바꾼다"로 읽어서
지운 것이 저장되지 않는다.

### 근무 위치 (요청)

구글은 재택·사무실 표시를 **`eventType: 'workingLocation'`인 종일 일정**으로 든다. 읽는
쪽은 PR5부터 있었고(칩이 아니라 **날짜 칸 우측 상단의 한 마디** — 그 날의 상태이므로)
쓰는 쪽을 이번에 붙였다. **새 스코프는 없다** — 이미 승인된 `calendar.events`로 쓴다.

- **기본 캘린더에만.** 구글이 이 일정을 다른 캘린더에 받지 않는다. 그래서 진입점은 기본
  캘린더가 **쓸 수 있고 지금 보고 있을 때만** 뜬다(꺼 둔 캘린더에 쓰면 고른 값이 화면에
  나타나지 않아 고장으로 읽힌다).
- **본문**: `eventType` + `start`/`end` + `workingLocationProperties`(`homeOffice` /
  `officeLocation.label` / `customLocation.label`) + `visibility: 'public'` ·
  `transparency: 'transparent'`(그 날의 상태라 바쁨으로 잡히면 회의실·한가함 조회에
  걸린다). 제목은 **지어 넣지 않는다** — 구글의 클라이언트가 갈래로 보여 준다.
- **일정 하나는 언제나 하루다.** 구글이 못박아 뒀다(라이브 제보의 400):
  `malformedWorkingLocationEvent` — *"An all-day working location event must be exactly
  one day long."* 그래서 `WorkLocationDraft.endDate`는 **한 일정의 길이가 아니라 며칠에
  걸 것인가**를 뜻하고, 그 해석은 `workLocationDays` **한 곳**에서만 한다(`workLocationWhen`은
  그 값을 아예 보지 않아 여러 날이 한 일정에 실리는 상태를 만들 수 없다).
- **구간은 하루하루에 하나씩**(`useGoogleCalendar.saveWorkLocation`): 고른 구간의 날마다
  있으면 PATCH, 없으면 POST를 차례로 보내고(한꺼번에 날리면 속도 제한) 마지막에 한 번
  새로 읽는다. 상한 `WORK_LOCATION_MAX_DAYS`(31) — 넘으면 팝업이 **막고 이유를 말한다**
  (조용히 잘라 저장하면 고른 것과 저장된 것이 달라진다).
- **`시간 추가`**를 켜면 그 하루 안의 시각 구간이 된다(구글도 시각 근무 위치를 하루로
  제한한다) — 구간과 함께 쓰이지 않는다.
- **고치기는 바뀐 것만**(`workLocationPatch(draft, whenChanged)`) — 갈래·이름만 바꿨으면
  `workingLocationProperties` 하나뿐이다(`workLocationWhenChanged`가 판단). 날짜를 싣지
  않는 저장은 그 사이 구글이 스스로 판을 올려도 412로 막히지 않는다.
- **팝업이 보여 주는 것은 그 하루다.** 데이터가 실제로 하루 단위이므로(위 제약) 걸려 있는
  날을 열면 그 날이 뜨고, 종료 날짜를 뒤로 밀면 **그만큼 날이 더 걸린다** — 구간 밖의
  날은 건드리지 않는다(지우기도 그 하루만). 반복되는 근무 위치는 회차가 하루짜리로 오므로
  그 회차의 갈래·이름을 고치는 것은 그대로 된다.
- **매주 되풀이는 하루짜리에만 뜬다**(요청 — 구글의 `근무 위치 수정` 화면과 같은 두
  선택: `선택한 날짜만` / `…부터 매주`). 저장은 `repeat: 'weekly'` → **일정 하나 +
  `RRULE:FREQ=WEEKLY;BYDAY=<요일>`**이고 회차는 구글이 펼친다(`workLocationDays`가 그때
  하루만 돌려주므로 구간처럼 여러 날에 나뉘지 않는다). 요일을 규칙에 **명시**하는 이유:
  나중에 시작일만 옮기는 PATCH에서 `DTSTART`가 정하는 요일과 어긋날 수 있다.
  - **구간에서는 되풀이 칸이 사라진다** — 하루씩 여러 일정으로 나가는 것에 되풀이를
    얹으면 사용자가 고른 적 없는 모양이 된다.
  - **이미 매주 반복인 근무 위치(회차)를 열면** `매주`가 켜진 채로 뜨고, 그때 두 선택은
    **바꾸는 범위**가 된다(구글의 그 화면과 같은 뜻):
    - `매주` 유지 → 회차가 아니라 **그 반복 자체**(`recurringEventId`가 가리키는 원본)를
      PATCH한다. 규칙은 이미 그 일정에 있으므로 싣지 않는다.
    - `선택한 날짜만` → 그 **회차를 DELETE**하고 그 날짜에 홀로 선 근무 위치를 POST한다
      (데이터로도 그게 "그 날만"이다).
  - **회차를 PATCH하지 않는다.** 라이브에서 그 요청이 400
    `malformedWorkingLocationEvent`("modify a working location event in a way that is not
    valid for this event type")로 거절됐다 — 구글은 근무 위치 회차의 수정을 막는다.
    그러니 거절되는 요청을 아예 만들지 않는다(저장 규칙은 `saveWorkLocation`).
  - 반복 규칙 자체를 **캘린더 설정에서** 정하는 길(구글의 그 화면)은 우리 스코프로 닿지
    않는다 — 그건 여전히 구글 캘린더의 일이다.
- **우리 표에는 없는 개념이다**(§18의 `calendar_events`) — 구글 전용이다.

구글이 거절하면(400) 사유가 그대로 화면·콘솔에 남는다(아래 `PATCH는 바뀐 것만` 참고).
Workspace 정책이나 계정 종류에 따라 이 기능이 꺼져 있을 수 있으므로, 실패하면 그 문장이
유일한 단서다.

### 일정 색은 구글이 정하는 만큼(요청)

값이 `colorId`이므로 **고를 수 있는 색은 구글이 정한다** — 표에 없는 번호를 우리가 지어
내면 그 저장이 거절된다. 그래서 `googleColorOptions`는 목록을 적어 두지 않고 `/colors`가
돌려준 번호를 **번호순으로 전부** 싣는다(응답 순서에는 보장이 없다). 구글이 팔레트를
넓히면 화면도 그만큼 넓어진다(24개를 주면 24칸). 이름은 아는 열한 개는 구글의 낱말
(라벤더·세이지·토마토…), 모르는 번호는 hex에서 계산한다 — 글자 없는 동그라미에 접근
이름·툴팁이 없으면 무슨 색인지 알 길이 없다. 팔레트를 못 받으면 폴백 표
(`GOOGLE_EVENT_COLORS`)로 그리고 콘솔에 왜 못 받았는지 남긴다.

**몇 색을 받았는지도 콘솔에 남긴다** — `[geurio] 구글 이벤트 색 N개(번호 …)`. "구글 웹
UI에는 24색인데 우리 팝업은 11칸"의 답이 그 한 줄에 있다: 이 API가 11개를 주면 나머지는
`colorId`로 지정할 수 없고(보내면 거절된다), 24개를 주면 화면도 24칸이 된다 — 코드는
그대로다.

### 연결 유지 — refresh token (0035 + `google-oauth`)

검수를 통과한 뒤 **auth-code 흐름**으로 바꿨다. 브라우저는 인가 코드만 받고, Edge Function
`google-oauth`가 client secret으로 교환해 **refresh token을 서버에 보관**한다(0035
`google_credentials`). 액세스 토큰이 만료되면 그 함수가 **팝업 없이** 새로 발급한다.

예전에는 브라우저 전용 토큰 흐름뿐이라 refresh token이 없었고, 갱신하려면 GIS를 다시
불러야 하는데 그건 조용한 갱신(`prompt: ''`)이라도 **팝업 창을 연다**. 그래서 한 시간마다
사용자가 "다시 연결"을 눌러야 했다(제보).

**스코프는 늘지 않았다.** 유지는 스코프가 아니라 흐름의 문제다 — 필수 둘·선택 셋 그대로다.

#### 표 (0035)

| 칼럼 | 뜻 |
| --- | --- |
| `user_id` | `auth.users` PK, `on delete cascade`(탈퇴 시 함께 삭제) |
| `refresh_token` | 구글이 준 갱신 토큰 — **밖으로 나가지 않는다** |
| `scope` | 그때 실제로 승인된 범위 |
| `google_email` | 어느 구글 계정인가(표시·계정 전환 감지) |

RLS를 켜고 **정책을 하나도 두지 않는다** + `revoke all ... from anon, authenticated`.
refresh token은 만료가 없어서, 브라우저에 한 번이라도 닿으면 유출 표면이 한 시간에서
무기한으로 늘어난다. 그래서 service role(= Edge Function)만 만진다.

#### 함수 (`supabase/functions/google-oauth`)

세 동작 모두 호출자의 **JWT로 누구인지 먼저 확인하고** 그 사람의 행만 만진다(요청 본문에
사용자 id를 받지 않는다).

| action | 하는 일 |
| --- | --- |
| `exchange` | 코드 → 토큰. **리디렉션 URI를 요청 본문으로 받는다**(웹 GIS 팝업은 약속값 `postmessage`, 설치형 앱은 `https://…/auth/gcal`) — 코드를 받을 때 쓴 값과 같아야 구글이 교환해 준다. refresh token이 오면 upsert, 안 오면 기존 행 유지 |
| `refresh` | 저장된 refresh token으로 액세스 토큰 발급. `invalid_grant`이면 행을 지우고 `revoked` |
| `disconnect` | 구글에 revoke → 행 삭제 |

**시크릿이 없으면 아무 일도 하지 않는다** — `{ ok: false, reason: 'not-configured' }`를 200으로
돌려주고, 클라이언트는 예전 흐름(브라우저 토큰 + 한 시간 뒤 "다시 연결")으로 굴러간다.
배포 순서와 무관하게 앱이 깨지지 않는다.

#### 소유자가 직접 해야 하는 것

1. Google Cloud Console → 사용자 인증 정보 → 그 **웹 클라이언트**의 클라이언트 보안 비밀번호를 복사
   (스코프·게시 상태·브랜딩은 **건드리지 않는다** — 검수를 통과한 값이다)
2. `supabase secrets set GOOGLE_CLIENT_ID=<...> GOOGLE_CLIENT_SECRET=<...>`
3. `supabase functions deploy google-oauth`
4. 마이그레이션 0035 적용(GitHub 연동은 main 머지 시 자동)

넷을 다 하기 전까지는 지금과 똑같이 동작한다(폴백).

#### 확인

- 연결 → 한 시간 뒤(또는 `mf_gcal_token`을 지운 뒤) 새로고침 → **팝업 없이** 일정이 그대로 뜬다
- `select user_id, scope, google_email, updated_at from google_credentials;` → 그 사용자의 행 하나
  (`refresh_token`은 조회하지 말 것 — 값 자체가 자격 증명이다)
- 연결 해제 → 행이 사라지고, 구글 계정의 타사 앱 권한에서도 빠진다

#### 함수는 **손으로** 배포한다 — 그것이 `redirect_uri_mismatch`의 정체 (제보)

앱에서 연동하면 `구글 연결을 확인하지 못했어요.`만 뜨고 이어지지 않았다. 그 문장은 우리
**폴백**이고, 서버가 돌려준 `reason`·`detail`은 버려지고 있었다 — 원인이 무엇이든 사용자와
우리가 보는 것이 같았다.

배포 순서가 원인이다: **마이그레이션은 GitHub 연동이 main 머지 때 자동으로** 올리지만
`supabase/functions/*`는 **`supabase functions deploy`를 손으로** 해야 한다. 그래서 앱은 새
판(코드를 `/auth/gcal`로 받는다)인데 서버는 옛 판(`postmessage`로 교환한다)인 창이 생기고,
구글은 두 값이 다르면 `redirect_uri_mismatch`로 거절한다.

두 겹으로 고쳤다:

- **사유를 드러낸다** — `serverFailureMessage(reason, detail)`가 자주 나는 둘(`redirect_uri_mismatch`
  = 함수 재배포, `invalid_grant` = 코드 만료)은 **무엇을 해야 하는지까지** 말하고, 나머지는
  구글의 원문을 그대로 싣는다. 콘솔에도 `[geurio] google-oauth 실패 <reason> <detail>`이 남는다.
- **함수를 배포한다** — 클라이언트 쪽 수리로는 이 사고가 끝나지 않는다. 앱 판을 올릴 때
  `google-oauth`도 함께 올려야 한다.

⚠️ **`supabase/functions/` 안을 고치면 `supabase functions deploy <name>`을 반드시 함께** —
그러지 않으면 앱만 새 판이 되어 조용히 거절당한다.

실측(2026-09-10): 콘솔 승인된 리디렉션 URI에 `https://geurio.com/auth/gcal`을 넣고
`supabase functions deploy google-oauth --project-ref <ref>`를 올린 뒤 **Windows 설치본에서
연동이 끝까지 이어졌다**. 배포 로그의 `WARNING: Docker is not running`은 무해하다 — Docker는
로컬에서 함수를 돌려 볼 때만 필요하고, 배포는 `Uploading asset (…)` 줄이 말하듯 API로 올린다.

배포가 성공했는데도 연동이 안 되면 **시크릿을 먼저 본다** — 값이 없으면 함수가 `not-configured`를
200으로 돌려주고 앱은 예전 흐름으로 조용히 물러나므로, 배포만 보고는 알 수 없다:

```bash
supabase secrets list --project-ref <ref>   # GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET
```

시크릿을 새로 넣었으면 **함수를 한 번 더 배포**한다(새 값을 실은 인스턴스로 갈아 끼운다).

#### 개인정보처리방침

이 변경으로 **서버에 보관하는 것이 하나 늘었다** — 방침 §4(갱신 토큰 항목)·§5(수탁 예외)·
§6(자격 증명 격리)을 함께 고쳤다. 저장 위치·수명·보호 수단을 바꾸면 **방침도 같이** 고쳐야
한다(방침이 실제 구현과 어긋나면 그 자체가 반려 사유다).

### 설치형 앱의 연동 — 시스템 브라우저 + 딥링크 (제보)

앱에서 `연결하기`를 누르면 **그 자리에서** `팝업이 막혔어요`가 떴고, 브라우저에서 동의를
마쳐도 앱으로 이어지지 않았다. 원인은 하나다 — 웹의 GIS 흐름은 `window.open`으로 동의
창을 띄우는데 **앱 창은 우리 출처만 띄우므로**(셸의 `setWindowOpenHandler`) 그 요청이
시스템 브라우저로 넘어가고, GIS에게는 `window.open`이 `null`을 돌려준 것으로 보인다
(`popup_failed_to_open`). 넘어간 창은 `opener`가 없어 코드를 돌려줄 곳도 없다.

그래서 설치형 앱은 **GIS를 아예 지나지 않고** 로그인과 같은 길(RFC 8252, §21)을 쓴다:

1. 앱이 동의 주소를 만들어 **시스템 브라우저**에서 연다(`response_type=code`,
   `access_type=offline`, `prompt=consent` — 이 둘이 refresh token을 받는 짝이다).
2. 브라우저: 동의 → `https://geurio.com/auth/gcal?code=…&state=…`
3. 그 페이지가 `geurio://gcal?code=…&state=…`로 앱을 깨운다.
4. 앱이 `state`를 대조하고 코드를 **Edge Function `google-oauth`**에 넘겨 교환한다
   (client secret은 서버에만 있다).

**스코프는 하나도 늘지 않는다** — 검수를 통과한 다섯 그대로다.

> **소유자가 해야 할 콘솔 작업 한 줄**: Google Cloud Console → API 및 서비스 → 사용자
> 인증 정보 → 그 **웹 클라이언트** → **승인된 리디렉션 URI**에
> `https://geurio.com/auth/gcal` 추가. 리디렉션 URI는 **검수 대상이 아니므로** 스코프·게시
> 상태·브랜딩은 건드리지 않는다. 기존 URI(Supabase 콜백)는 **지우지 말 것** — 웹 로그인이
> 계속 쓴다. 이 줄이 없으면 브라우저에서 구글의 `redirect_uri_mismatch` 오류 화면이 뜬다.

교환 요청의 `redirect_uri`는 **코드를 받을 때 쓴 값 그대로**여야 한다(구글의 규칙) — 웹의
GIS 팝업은 약속값 `postmessage`, 앱은 위 핸드오프 주소다. 함수는 그 값을 받되
`postmessage`이거나 `https://…/auth/gcal`인지 **모양을 확인한다**(우리 시크릿을 쓰는
자리라 좁혀 둔다).

서버 흐름이 없는 배포(로컬·데모·함수 미배포)에서는 코드를 받아 와도 교환할 곳이 없으므로
**창을 열지 않고** 그 사실을 문장으로 말한다.

### "다시 연결"은 탭 전체가 함께 안다 (제보)

설정은 `다시 연결`이라 하는데 **일정 화면·대시보드 위젯·새 일정 팝업은 연결된 것처럼**
보였다. `needsReauth`가 `useGoogleCalendar` **인스턴스마다** 따로 있었기 때문이다 — 연결
상태는 계정 하나의 사실이라 화면마다 다를 수 없다. 지금은 토큰과 같은 자리
(`googleCalendar.ts`)에 두고 바뀌면 모두에게 알린다.

그리고 그 상태에서는 **구글이 화면에서 빠진다**: 이 탭이 기억한 일정(`eventCache`)은
그리지 않고(공휴일 칠·근무 위치도 같은 목록에서 오므로 함께), 새 일정 팝업의 "저장할
캘린더"에서 구글 목적지가 사라진다(골라 봐야 저장이 실패한다). 다시 연결하면 곧바로
돌아온다.

### 두 원천의 경계

구글에 만든 일정은 **구글에만** 남는다(우리 표에 사본을 두지 않는다) — 연동을 끄면 화면에서
사라지고 구글에는 그대로 있다. 반대로 Geurio 일정(§18)은 구글에 나타나지 않는다. 새 일정
팝업의 `저장할 캘린더`와 발치 문구가 그 경계를 말한다.

### 참석자 명단이 잘려 오는 일정

구글은 두 경우에 **참석자 배열을 온전히 주지 않는다**: 참석자가 아주 많으면
`attendeesOmitted: true`로 잘라 보내고, 주최자가 "참석자 명단 보기"를 껐으면
(`guestsCanSeeOtherGuests: false`) 나 자신만 담아 준다. 이 상태에서 우리가 들고 있는
배열을 **되돌려 쓰면 나머지 참석자가 조용히 초대 취소된다** — PATCH는 `attendees`를 통째로
바꾸기 때문이다(§19 「쓰기 규칙」).

그래서 `attendeesLocked()`가 그 두 경우를 잡아 ① 화면에 안내를 띄우고(참석자·참여 여부
칸을 잠근다) ② **쓰기 경로에서 `attendees`를 아예 싣지 않는다**(제목만 고치면 PATCH의
키가 `summary` 하나다). 명단을 고치려면 Google 캘린더에서 한다. 주최자 본인이 명단 보기를
껐을 뿐인 경우(`organizer.self`)는 배열이 온전하므로 잠그지 않는다.

### 공휴일

id가 `#holiday@group.v.calendar.google.com`으로 끝나는 캘린더는 **공휴일 원천**으로 본다.
그 일정은 칩으로 그리지 않고 **날짜 옆에 이름**을 적는다. 다만 그 캘린더에는 공휴일만이
아니라 **24절기·기념일·종교 절기**가 함께 들어 있어서(입추·칠석…) 전부 칠하면 달이 통째로
분홍이 된다 — 구글이 종류를 적어 두는 `description`을 읽어(`isDayOffHoliday`) **실제로
쉬는 날일 때만** 칸과 숫자를 일요일 색으로 그린다. 표기가 없거나 모르는 값이면 칠하지
않는다(이름은 남는다).

### 확인

연결 뒤 `sessionStorage.mf_gcal_token`이 차고(그 안에 `scope`가 두 스코프를 다 담아야
한다), 워크스페이스 블롭(`workspaces.data`)에 `google.calendars`가 남으며 **토큰은 남지
않는다**. 일정이 안 보이면 순서대로 본다: ① 설정 구획에 오류 문구가 있는가(스코프
미승인·테스트 사용자 아님) ② 그 캘린더가 목록에서 체크돼 있는가 ③ 콘솔 네트워크 탭에서
`calendar/v3/calendars/.../events`가 200인가.

**저장이 안 될 때**: ① 설정·머리에 `다시 연결`이 떴는가(= 승인된 **필수** 스코프가
모자라다) ② 그 캘린더에 `보기 전용` 표시가 있는가 ③ 네트워크 탭의 `PATCH`/`POST`
상태 코드 — 403은 권한, 412는 그 사이 구글에서 바뀐 것.

**이름 검색이 안 될 때**: 참석자 입력의 접근 이름을 본다 — `참석자 이메일`이면 선택
스코프를 못 받은 것이고(`참석자 이름 또는 이메일`이면 열려 있다), 열려 있는데 결과가
없으면 개인 계정(디렉터리 없음)이거나 정말 없는 것이다. `people.googleapis.com` 요청의
403이 전자다.

**같은 사람의 이름이 자리마다 다를 때**(주최자는 이름, 참석자는 이메일 앞부분): 구글은
`organizer`에는 `displayName`을 실어 주지만 `attendees`에는 자주 비워 둔다. 앱은 **이름
장부**(`calendar/nameBook.ts`)에 받아 온 모든 일정의 주최자·참석자 이름과 디렉터리 검색
결과를 한곳에 적고 어느 자리에서든 거기서 읽으므로, 한 일정에서라도 이름이 온 사람은
다른 일정의 참석자 행에서도 같은 이름이다. 그래도 로컬파트로 남는 사람은 **어느 일정에도
이름이 실려 오지 않고 디렉터리에도 없는** 사람이다(저장된 연락처의 이름은 `contacts.readonly`
— 새 스코프 — 가 필요해 받지 않는다). 장부는 탭 안에서만 살고 계정을 바꾸면 비운다.

**기존 일정의 참석자 일부만 이름이 올 때**: 두 가지가 겹쳐 있었다(2026-09, 라이브 로그).
디렉터리는 **별칭 주소**로 물어도 기본 주소가 첫 번째인 사람으로 답하므로 질의와 사람의
모든 주소(`emails`)를 맞춰 봐야 하고, 이름 조회 루프는 첫 답이 와 상태가 바뀌어도 취소되면
안 된다(취소되면 남은 사람은 "물어봤다"로 남아 영영 로컬파트). 지금은 둘 다 고쳐졌으니,
그래도 남는 사람은 응답 `people: []`인 사람이다.

**회의실 구획이 안 보일 때**: `admin.directory.resource.calendar.readonly`를 승인받지
못했거나, 승인은 됐지만 조직이 **관리자 동의**를 요구해 `admin.googleapis.com` 요청이
403인 것이다. 후자는 앱에서 풀 수 없다 — Workspace 관리자가 앱을 도메인에 허용해야 한다.

### 하지 않은 것

- **반복 규칙 고치기**(이미 있는 일정의 RRULE) — 구글에서 하도록 링크로 보낸다.
  새 일정에서 반복·Meet·참석자·회의실·공개·참여·알림은 모두 설정할 수 있다.
- **캘린더 사이 이동**(다른 캘린더로 옮기기) — 구글의 `move` API가 따로 있다.
- **웹훅·증분 동기화**(`syncToken`·push notification) — 서버가 있어야 한다. 지금은 달을
  옮길 때마다, 그리고 위의 두 계기마다 그 구간을 다시 받는다(캘린더 하나에 요청 하나,
  한 달치). 실시간이 필요해지면 그때 Edge Function으로 watch 채널을 받는다.
