## 22. 일정 알림 (0038 `calendar_events.reminder_minutes`) — 서버는 보내지 않는다

요청: *"오전 10:30 일정에 10분 알림을 걸어 두면 10:20에 앱 알림과 OS 알림을 받고 싶다."*

### 마이그레이션

`0038_event_reminders.sql` — `calendar_events`에 `reminder_minutes int` 추가(+ 0~40320
범위 check). `null` = 알림 없음이고 **그게 기본**이다: 아무것도 저절로 뜨지 않는다.

```sql
select column_name, data_type from information_schema.columns
 where table_name = 'calendar_events' and column_name = 'reminder_minutes';
```

미적용 서버에서도 앱은 깨지지 않는다 — 어댑터가 그 칼럼을 뺀 행으로 **한 번 더** 저장하고
콘솔에 `반복·알림 없이 저장했어요(마이그레이션 0034·0038 확인)`를 남긴다(배포 순서 안전).

### 왜 서버 푸시가 아닌가 (이 결정이 설계의 뿌리다)

이 칼럼은 **누가 언제 알림을 원하는가**만 담고, 띄우는 일은 브라우저·앱이 한다
(`apps/web/src/features/reminders/`). 서버가 알림을 보내려면 일정의 제목·시각을 서버에
쌓아야 하는데, 개인정보처리방침이 캘린더 데이터를 *"브라우저에서 화면에 그리는 데만 쓰고
서버·수탁사를 거치지도 저장되지도 않는다"*고 **명시**하고 있고(§4·§5·§6) **구글 민감
스코프 검수가 그 방침으로 통과했다**. 로컬 예약이면 방침·스코프를 한 줄도 건드리지 않고
"앱이 켜져 있을 때"를 온전히 덮는다.

| 상황 | 지금 | 왜 |
| --- | --- | --- |
| 앱·탭이 열려 있다(최소화 포함) | ✅ | 30초 주기 확인 + OS 알림 |
| 데스크톱 앱 창을 닫음 | ✅ | 트레이(macOS는 독)에 남아 렌더러가 계속 돈다 — 아래 §22d |
| 데스크톱 앱 완전 종료 | ❌ | 그때는 멎는다 — 사용자가 고른 것이다 |
| 브라우저 닫힘 | ❌ | 서버 푸시가 필요 |
| 모바일 앱 (닫혀 있어도) | ✅ | Capacitor 로컬 알림 — **OS가 예약을 들고** 있어 서버 없이 된다. 아래 §22c |
| 구글 일정 | ✅(기본 꺼짐) | 구글이 이미 보내므로 켜면 둘이 된다 — 아래 §22b |

Geurio 일정에 한해서는 서버 푸시가 **방침 개정 없이** 가능하다(그 값이 원래 우리 표에
있다) — "앱을 완전히 닫아도 알림"이 필요해질 때의 다음 수순이고, 그때도 구글 일정은
올리지 않는다.

### 왜 `setTimeout` 하나가 아니라 주기 확인인가

① 백그라운드 탭의 타이머는 크롬이 1분에 한 번으로 조인다 ② **절전 중에는 타이머가 아예
돌지 않는다**. 그래서 30초마다 "지금 띄울 것"을 훑고, 지나간 알림은 **5분 유예** 안이면
늦게라도 띄우고 그보다 오래면 조용히 넘긴다(어제 알림이 오늘 앱을 켜자마자 뜨지 않게).
설치형 앱은 `backgroundThrottling: false`로 그 조임 자체를 없앤다(셸만 정할 수 있다).

### 종일 일정

v1은 **시각 있는 일정만** 알림을 갖는다 — 종일에 "10분 전"은 자정 10분 전이라 뜻이
어긋나고(구글도 종일 알림을 "며칠 전 몇 시"라는 다른 표기로 다룬다) 우리 칩은 분 단위뿐이다.
종일로 바꾸면 정규화가 값을 **지운다**(저장본만 봐도 무엇이 뜰지 알아야 한다).

### 진단

| 증상 | 볼 곳 |
| --- | --- |
| 알림이 안 뜬다 | 설정 › `일정 알림`이 켜져 있는가 · 그 행의 문구가 권한 상태를 말한다 |
| 앱 알림만 뜬다 | OS 알림 권한이 `denied` — 브라우저·OS 설정에서 풀어야 한다(앱에서 못 푼다) |
| 저장이 안 된다 | 콘솔 `반복·알림 없이 저장했어요` → 0038 미적용 |
| 같은 알림이 두 번 | `localStorage.mf_reminded`(키 = `일정#회차@알림시각`) 확인 |

### 22b. 구글 일정 알림 (2단계) — 마이그레이션 없음

**서버는 한 줄도 바뀌지 않는다.** 구글 일정의 알림 값은 구글이 들고 있고, 우리는 이미
읽고 있다(`reminders.useDefault` / `overrides`). 2단계가 더한 것은 **띄우는 쪽**뿐이다.

**기본이 꺼짐**인 이유는 1단계와 정반대다: 그 알림은 **구글이 이미 보낸다**(구글 캘린더
앱·브라우저 알림). 켜진 채로 시작하면 같은 회의에 알림이 둘 뜨는 것이 기본 동작이 되고
그건 고장으로 읽힌다. 설정 › `일정 알림` 아래 하위 토글이고(`mf_reminders_google`,
이 기기) **연동돼 있을 때만** 그린다.

#### 몇 분 전에 띄울까 — 두 곳에서 온다

| 일정의 `reminders` | 우리가 쓰는 값 |
| --- | --- |
| `overrides: [{popup, 10}]` | 10분 — 그 일정에 직접 건 알림 |
| `useDefault: true` | **그 캘린더의 기본 알림**(`calendarList`의 `defaultReminders` 첫 팝업) |
| `useDefault: false`, overrides 없음 | 없음 — 사용자가 꺼 둔 것이다 |
| 기본을 모르는 캘린더 | 없음 — 모르는 값을 지어내지 않는다 |

대부분의 구글 일정이 `useDefault`라, 캘린더 기본을 모르면 이 기능이 사실상 비어 버린다.
그 값은 **`calendarList`에만 있고 일정 응답에는 없으므로** 목록을 받을 때 함께 챙긴다
(`GoogleCalendarMeta.defaultMinutes`).

#### 캘린더 거울 (`mf_gcal_remind_cals`)

정본은 워크스페이스 블롭(`google.calendars`)이고 그것을 읽는 것은 홈이다. 그런데 알림
스케줄러는 문지기(`RequireAuth`) 안에 있어 **에디터에서도** 도는데 에디터는 그 블롭을
한 번도 읽지 않는다 → 홈이 알고 있을 때 이 기기에 적어 둔다(`storeReminderCalendars`).

```js
// 브라우저 콘솔
JSON.parse(localStorage.getItem('mf_gcal_remind_cals'))
// → [{ id: 'me@example.com', defaultMinutes: 10 }]
```

담는 것은 **지금 보여 주는 캘린더 + 그 기본 알림**뿐이다: 숨긴 캘린더의 일정이 알림으로
뜨면 화면과 어긋나고, 공휴일 캘린더는 종일이라 담지 않는다. 목록이 **도착하기 전에는
적지 않는다**(그때는 주소로 더한 것뿐이라 구독 캘린더를 통째로 지운 거울이 된다).

#### 빼는 것 넷

종일(자정 기준이라 뜻이 어긋난다) · 공휴일 · 근무 위치(회의가 아니다) · **내가 거절한
회의**(구글도 알리지 않는다).

#### 조회 비용

켜 둔 사람에게만, 알림 창(오늘~+2일)에 대해 **캘린더 수만큼** 요청이 5분 주기 + 깨어나는
순간에 난다. 끈 사람에게는 **왕복이 한 번도 나가지 않는다**(테스트로 고정). 토큰은
`ensureGoogleToken`으로 **팝업 없이** 받고, 못 받으면 조용히 물러난다 — 알림 때문에 동의
창이 저절로 뜨면 안 되고(§19 재로그인 팝업), "다시 연결"을 세우는 것은 화면의 일이다.

#### 진단

| 증상 | 볼 곳 |
| --- | --- |
| 구글 하위 토글이 없다 | 연동돼 있는가(설정 › 계정 설정 › Google 캘린더 연동) · 위 `일정 알림`이 켜져 있는가 |
| 켰는데 안 뜬다 | `mf_gcal_remind_cals`가 비어 있지 않은가(홈·일정 화면을 한 번 열면 채워진다) |
| 특정 일정만 안 뜬다 | 그 일정이 `useDefault`인데 캘린더 기본이 없을 수 있다 — 구글에서 그 캘린더의 기본 알림 확인 |
| 알림이 둘 뜬다 | 정상 — 구글도 보내고 우리도 보낸다. 이 토글을 끄면 구글 것만 남는다 |

### 22c. 모바일 로컬 알림 (3단계) — 마이그레이션 없음

1·2단계는 **앱이 켜져 있을 때**만 동작한다(우리가 30초마다 훑는다). Capacitor 앱에서는
**OS가 예약을 들고 있어** 앱이 닫혀 있어도, 기기를 재부팅해도 그 시각에 뜬다
(`@capacitor/local-notifications`, 플러그인이 `BOOT_COMPLETED`에 다시 심는다).

**서버는 한 줄도 바뀌지 않는다** — 클라이언트가 앱이 열려 있는 동안 앞으로 며칠치를
OS에 옮겨 둘 뿐이다. 개인정보처리방침의 "캘린더 데이터는 브라우저에서만 쓰고 서버에
저장하지 않는다"(§4·§5·§6)도 그대로다: 예약은 기기 안에서 끝난다.

#### 무엇을 맡기는가

| 값 | 근거 |
| --- | --- |
| 창 7일(`NATIVE_WINDOW_DAYS`) | 웹은 2일이면 되지만(켜져 있을 때만 돈다) 여기서는 주말 내내 앱을 열지 않은 사람의 월요일 아침이 덮여야 한다 |
| 최대 48건(`NATIVE_MAX_PENDING`) | iOS는 앱당 64건까지만 들고 있고 **넘치면 조용히 버린다** — 여유를 두고 가까운 것부터 채운다 |
| 지난 알림은 제외 | OS 예약은 미래만 뜻이 있다. 지나간 알림을 늦게라도 띄우는 일은 앱이 켜져 있을 때의 5분 유예가 맡는다 |
| id = `해시(key@fireAt\|title)` | 일정을 옮기거나 제목을 고치면 **다른 알림**이 되어 옛 예약이 거둬진다. 회차는 키가 이미 구분한다 |

동기화는 **집합 차이**다(`planNativeSchedule`): 걸려 있는 id와 있어야 할 id를 견줘 빠진
것만 심고 남는 것만 거둔다. 통째로 지웠다 다시 심으면 곧 뜰 알림이 그 찰나에 사라진다.
알림을 끄면 목록이 비어 **같은 경로로** 전부 거둬진다(끄는 길을 따로 만들지 않는다).

#### 누가 띄우는가 — 둘이 되지 않게

권한이 있으면 OS가 띄우고 **우리 주기 확인은 판단에서 빠진다**. 앱이 떠 있는 동안의
토스트는 플러그인의 수신 이벤트(`localNotificationReceived`)로 잇는다(iOS는 그때 배너를
감추므로 그것이 유일한 표시다). 권한이 없으면 맡길 수 없으므로 **예전처럼 우리가**
훑어 띄운다. 권한을 아직 모르는 동안(앱을 켠 직후)에는 **아무도 띄우지 않는다** —
모르는 채로 우리가 먼저 띄우면 곧이어 OS도 띄운다.

#### 함정 셋(코드 주석과 같은 내용)

- **정확 알람을 쓰지 않는다**(`isExactNotification: false`). 안드로이드 12+에서 정확
  알람은 따로 허용받아야 하고, 플러그인은 허용돼 있지 않으면 `schedule()` 도중
  **시스템 "알람 및 리마인더" 설정 화면을 연다** — 앱을 열면 저절로 도는 동기화가
  누르지도 않은 시스템 화면을 띄우면 안 된다(§19 재로그인 팝업과 같은 규칙). 대가는
  몇 분의 오차이고 `allowWhileIdle: true`로 Doze는 넘긴다.
- **알림 아이콘은 흰 글리프 + 투명 배경**(`ic_stat_geurio`). 안드로이드는 색을 버리고
  알파만 남기므로 런처 아이콘을 쓰면 상태 표시줄에 흰 네모가 뜬다.
- **플러그인 객체를 async 함수에서 그대로 `return`하지 않는다.** 반환 처리가 thenable
  인지 보려고 `.then`을 읽는데 Capacitor 플러그인은 모르는 이름을 전부 네이티브 호출로
  넘기는 프록시라 그 순간 거부된다 — 상자에 담아(`{ p }`) 돌려준다.

#### 진단

| 증상 | 볼 곳 |
| --- | --- |
| 설정에 `일정 알림` 행이 없다 | 네이티브에서는 웹 `Notification`이 없으므로 플러그인 권한으로 판단한다 — 플러그인이 네이티브에 등록됐는지(`android/app/capacitor.build.gradle`에 `capacitor-local-notifications`) |
| 앱을 닫으면 안 온다 | 권한이 `granted`인가 · 그 알림이 창(7일) 안이고 미래인가 · 48건 상한에 밀리지 않았는가 |
| 몇 분 늦게 온다 | 정상 — 위의 정확 알람 트레이드오프 |
| 상태 표시줄 아이콘이 흰 네모 | `capacitor.config.ts`의 `LocalNotifications.smallIcon`과 `res/drawable-*/ic_stat_geurio.png` |
| 알림이 둘 뜬다 | 권한 판정이 늦어 우리도 띄운 경우 — 앱 로그에서 `nativeOwned`가 `true`로 서는지 |

### 22d. 데스크톱 트레이 상주 (4단계) — 마이그레이션 없음

설치형 앱에서 **창을 닫아도** 알림이 계속 오게 한다. 알림을 띄우는 것은 렌더러의 주기
확인이므로, 창을 파괴하면 그 순간 스케줄러도 사라진다 — 그래서 닫기를 **숨기기**로 바꿔
창(=렌더러)을 살려 둔다. 모바일(§22c)이 OS에 예약을 **맡기는** 것과 달리, 여기서는
**우리가 계속 돌아** 3단계의 장치(주기 확인·유예·중복 방지)를 그대로 쓴다.

**서버도 웹 번들의 알림 규칙도 바뀌지 않는다** — 셸이 창을 살려 두고, 웹은 설정 두 행과
"알림을 누르면 창을 되찾는 길"만 더한다.

#### 규칙(셸의 순수 함수가 정한다 — `apps/desktop/src/shell.ts`)

| 판단 | 규칙 | 왜 |
| --- | --- | --- |
| 숨길까(`canStayInBackground`) | macOS는 언제나, 그 밖은 **트레이가 실제로 만들어졌을 때만** | 숨겼는데 트레이도 독도 없으면 창을 되찾을 길이 사라진다 |
| 트레이를 둘까(`usesTray`) | macOS 제외 | 독 아이콘이 이미 "실행 중"이자 되돌아오는 길이다(그 플랫폼 관례) |
| 창 없이 시작할까(`shouldStartHidden`) | 로그인 자동 실행(`--hidden`·`wasOpenedAtLogin`)이고 **상주할 수 있을 때만** | 닿을 길 없는 프로세스를 만들지 않는다 |
| 로그인 자동 실행을 내줄까(`supportsOpenAtLogin`) | Windows·macOS | Electron의 `setLoginItemSettings`가 Linux를 무시한다 |

기본은 **켜짐**이고(Slack·Teams·Discord와 같다), 대신 **처음 숨길 때 한 번 알린다** —
그 안내는 **실제로 띄운 뒤에만** "알렸다"로 기록한다(못 띄운 환경이면 다음에 다시 알린다).

#### 상태의 정본은 셸이다

상주 여부는 `userData/settings.json`, 로그인 자동 실행은 **OS**(`getLoginItemSettings`)가
들고 있다. 렌더러는 사본을 만들지 않고 `backgroundState()`가 돌려주는 것을 그대로 그리며,
토글도 **바뀐 뒤의 상태**를 돌려받는다 — MSIX 컨테이너처럼 로그인 항목을 받아들이지 않는
환경에서는 스위치가 제자리로 돌아가 사실을 말한다(거짓말을 하지 않는다).

`supported`가 거짓이면 설정에 **그 자리를 그리지 않는다**: 브라우저·PWA, 4단계 이전
설치본(창구 자체가 없다), 트레이가 없는 리눅스 데스크톱.

#### 함정 넷

- **AUMID**(`app.setAppUserModelId`)가 `electron-builder.yml`의 `appId`와 달라지면
  Windows 토스트가 아예 뜨지 않거나 남의 이름으로 뜬다. 알림이 이 단계의 전부라 그 한
  줄이 기능의 전제다 — `packaging.test.ts`가 두 값을 묶어 둔다.
- **트레이 아이콘은 `resources/`에 둔다.** `build/`는 electron-builder가 쓰는 재료일 뿐
  앱에 담기지 않으므로, 거기 두면 개발 실행에서는 보이고 **설치본에서만** 사라져 상주가
  통째로 없어진다.
- **트레이 아이콘은 설정과 무관하게 늘 띄운다.** 끈 상태에서 아이콘까지 없애면 상주가
  "불가능한 환경"으로 읽혀 설정의 그 자리가 사라지고 다시 켤 길이 없어진다.
- **`before-quit`에서 종료 깃발을 세운다.** 닫기를 가로채는 규칙이 종료까지 막으면 앱을
  끌 수 없다.

#### 진단

| 증상 | 볼 곳 |
| --- | --- |
| 설정에 `앱을 닫아도 알림 받기`가 없다 | 셸 판이 4단계 이전이거나(`window.geurio.backgroundState`가 없다) 트레이를 만들지 못한 환경 |
| 닫으면 그냥 꺼진다 | 그 설정이 꺼져 있는가(`userData/settings.json`의 `background`) |
| 닫아 두면 알림이 안 온다 | 창이 **숨은 것인지 파괴된 것인지** — 트레이 `Geurio 열기`로 되살아나면 숨은 것이다 |
| Windows에서만 토스트가 없다 | AUMID ↔ `appId` 일치, 그리고 Windows 알림 설정에서 Geurio가 켜져 있는지 |
| 로그인해도 자동 실행이 안 된다 | 설정 스위치가 켜진 채 남아 있는가(제자리로 돌아갔다면 OS가 거부한 것이다 — MSIX는 매니페스트의 startupTask가 필요하다) |
